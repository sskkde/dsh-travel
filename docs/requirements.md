## 1. 项目背景与目标

### 1.1 背景

用户规划一次旅行时，需要在多个平台之间反复切换：社交平台（小红书、bilibili、知乎、抖音）看真实游记与避雷帖，旅行平台（携程、同程、大众点评、美团）查评价与价格，地图工具查路线，天气应用看穿衣。信息分散、筛选成本高、且难以汇总为一份可执行的行程方案。

DeepSeek Harness（DSH）提供了插件化的 Agent 扩展机制：插件可以注册工具（Tool）、技能（Skill）、UI 面板与 HTTP 路由，并复用宿主的 LLM、子代理、任务编排能力。这使「自然语言 → 自动化信息收集 → 结构化行程方案 → 可视化展示」的端到端体验可以在一个插件内实现。

### 1.2 项目目标

开发一个旅行规划 DSH 插件：用户以自然语言描述旅行需求，插件自动完成 **需求解析 → 多轮信息收集 → 信息检索（目的地情报 / 交通 / 出行建议）→ 行程方案生成 → 可视化 HTML 展示** 的全流程。

### 1.3 成功指标（验收口径）

1. 用户一句自然语言（如"帮我规划十一杭州三日游"）即可进入旅行规划流程；
2. 关键槽位（见 FR-2）收集完整后，全流程无需用户手工打开任何外部网站；
3. 产出一份包含 **实际可用的地图组件** 的 HTML 行程页（见 FR-7）；
4. 行程页中每条关键信息（景点/美食/避雷等）均可追溯到来源；
5. 任一外部数据源失效时，流程不中断，仅该部分降级标注（见 NFR-2）。

## 2. 术语与定义

| 术语 | 定义 |
|---|---|
| DSH | DeepSeek Harness，本插件运行所在的 Agent 宿主框架 |
| 插件（Plugin） | DSH 的扩展单元，可注册工具/技能/UI/路由 |
| 工具（Tool） | 插件注册给 LLM 调用的函数（如"查询火车票"） |
| 技能（Skill） | 以 SKILL.md 形式注册的领域指令集，供模型按需加载 |
| 槽位（Slot） | 行程规划所需的结构化输入项（目的地、日期等） |
| 行程页 | 插件最终产出的可视化 HTML 页面 |
| 意图命中 | 用户消息被识别为旅行规划意图，从而激活本插件 |
| planId | 一次旅行规划会话的持久化标识：首次信息登记时生成，跨修订与跨会话复用；对应工作区 `.dsh-travel/<planId>/` 目录与行程页路由（字段级契约见设计文档 §5.5） |

## 3. 用户场景（User Stories）

| 编号 | 用户故事 | 覆盖需求 |
|---|---|---|
| US-1 | 作为旅行者，我说"帮我规划下个月去成都的行程"，系统自动进入旅行规划模式并逐步问我缺的信息 | FR-1、FR-2 |
| US-2 | 作为旅行者，我一次性给出全部信息（时间/人数/预算/偏好），系统不再反复追问，直接开始检索 | FR-2 |
| US-3 | 作为旅行者，我想看到来自小红书/知乎等平台的真实评价与避雷信息，而不是营销软文 | FR-3 |
| US-4 | 作为旅行者，我希望系统比较飞机/高铁等方案并给出建议的出行指引 | FR-4 |
| US-5 | 作为旅行者，我想知道目的地的天气、怎么穿衣、要带什么东西 | FR-5 |
| US-6 | 作为旅行者，我拿到一份图文并茂的行程页：按天组织的行程、地图上的点位与路线、美食与住宿推荐 | FR-6、FR-7 |
| US-7 | 作为旅行者，我对某些安排不满意，可以要求调整（换酒店/压缩行程）后重新生成 | FR-6 |
| US-8 | 作为用户，我在任意会话里聊到旅行话题，插件按需激活，不影响其他正常使用 | FR-1、NFR-7 |

## 4. 范围

### 4.1 范围内（In Scope）

- 意图识别与插件激活（基于 DSH 技能/指令机制，具体见设计文档）
- 多轮对话式信息收集（槽位填充 + 确认）
- 目的地情报检索：景点、住宿、交通、美食、注意事项、避雷、推荐
- 交通方式检索与组合（机票/火车票/汽车票 + 市内交通衔接）
- 出行建议检索（天气、穿衣、物品清单等）
- 行程方案（按天组织的 itinerary）生成
- 可视化 HTML 行程页生成与展示（含可用地图组件）
- 结果追溯（来源标注）

### 4.2 范围外（Out of Scope）

- **预订与支付**：不代用户下单、锁价、支付（后续版本可评估）
- **实时价格承诺**：票价/房价为检索时点的参考值，不保证实时准确
- **多目的地复杂环线优化**：v1 聚焦单一目的地（或一城多日）；跨国多段行程不做深度优化
- **原生移动端**：行程页以 HTML Web 页面交付，不做 App
- **账号代登录**（用户提供账号密码由插件登录）不在任何版本范围内；登录态（会话态）抓取为可选增强（默认关闭），其授权/存储/清除边界见设计文档 §5.6

## 5. 功能需求

需求编号规则：FR-功能编号；优先级：P0（必须有）/ P1（应该有）/ P2（可以有）。

### FR-1 意图触发与插件加载（P0）

| 项 | 内容 |
|---|---|
| 描述 | 用户通过自然语言描述旅行需求（行程规划、目的地推荐等），系统识别意图命中后，动态加载本插件的工具与技能 |
| 触发示例 | "帮我规划五一去重庆的行程"、"推荐几个适合带老人玩的海边城市"、"我想下周去西安玩三天，帮我安排" |
| 触发范围 | 旅行规划、目的地推荐、行程安排、交通查询、游记/攻略检索等旅行领域意图 |
| 详细要求 | 1) 意图命中后激活本插件的工具集与领域指令；<br>2) 未命中时插件保持静默，不影响普通会话；<br>3) 命中后首条响应应说明将要收集哪些信息（透明性）；<br>4) 用户可显式退出/中断流程；<br>5) v1 主路径为完整规划流程；纯单点查询意图（仅查班次/仅查天气等）允许轻量直答（P1）：加载技能后直接调用对应检索工具返回，不强制槽位收集 |
| 验收标准 | ① 对 20 条旅行相关表述的意图命中率 ≥ 90%（人工标注集；"命中"=加载 travel-planner 技能或调用任一 travel_* 工具）；② 对 20 条非旅行表述的误触发率 ≤ 5%（"误触发"口径=非旅行意图的会话中调用 travel_* 工具或加载本技能） |

### FR-2 多轮对话式信息收集（P0）

| 项 | 内容 |
|---|---|
| 描述 | 模型通过问答形式与用户交互，获取旅行的基本信息。支持两种收集模式：**规划模式**（目的地必填）与**目的地推荐模式**（目的地为空） |
| 槽位清单 | **必填（规划模式）**：出发地、目的地、出行时间（日期或区间）、行程天数、出行人数；<br>**选填**：预算、偏好（景点类型/饮食偏好/节奏松紧）、同行人构成（老人/儿童/宠物）、特殊约束（无障碍、素食等） |
| 推荐模式 | 用户无明确目的地（如 FR-1 示例"推荐适合带老人玩的海边城市"）：目的地暂缺不视为收集缺口 -> 先收集约束（时间/出发地/预算/偏好/同行人）-> 系统基于检索生成 3~5 个候选目的地（含理由与来源）-> 用户选定后回注目的地槽位 -> 转入规划模式补齐剩余槽位 |
| 详细要求 | 1) 一次最多追问 2~3 个问题，不进行"审问式"连环提问；<br>2) 用户首条消息已含的信息不重复追问；<br>3) 用户一次性给全信息时直接进入确认环节；<br>4) 模糊回答（如"十一左右"）需一次澄清到可执行精度；<br>5) 槽位收齐后**回显确认清单**，用户可逐项修改；<br>6) 必填槽位缺失且用户拒绝提供时，采用合理默认值并明确告知假设 |
| 验收标准 | ① 确认清单与用户已提供信息逐字段一致（零冲突=无任何字段与用户原话矛盾）；② 平均追问轮次 ≤ 3；③ 用户中途修改任一槽位后，下游结果正确联动；④ 推荐模式下候选均带来源，用户选定后目的地槽位正确回注且不重复追问 |

### FR-3 目的地综合信息搜集（P0）

| 项 | 内容 |
|---|---|
| 描述 | 根据收集到的输入信息，搜索并抓取网络上关于旅行目的地的信息 |
| 信息类别 | ① 景点（含开放状态/门票/建议时长）；② 住宿（区域/类型/价位段）；③ 当地交通（机场车站衔接、市内出行方式）；④ 美食（特色菜/店铺/口碑）；⑤ 注意事项（证件、预约、限流、当地规定）；⑥ 避雷（差评、坑点、翻车案例）；⑦ 推荐（高口碑内容汇总） |
| 信息来源要求 | 1) **主流社交媒体（渠道三层优先级，用户决策 2026-09-01）**：<br>**第一层级（优先）**：小红书、抖音；<br>**第二层级**：bilibili、知乎；<br>**第三层级**：微博、豆瓣、贴吧、快手——获取真实用户评价；<br>2) **旅行/生活平台**：携程、同程、大众点评、美团——获取结构化评价与价格参考；<br>3) **腾讯地图 POI 搜索补充**：经腾讯位置服务检索 POI（含评分/人均/营业时间），作为社媒情报的结构化补充（方案见设计文档 §5.4） |
| 详细要求 | 1) 每条关键信息记录：内容摘要、来源平台、来源 URL、获取时间；<br>2) 多来源交叉验证：同一对象（如某景点）至少聚合 2 个来源，冲突信息需标注；<br>3) 信息时效性：优先近 12 个月内容，过期内容降权并标注时间；<br>4) 单来源抓取失败时降级继续（见 NFR-2），不阻塞整体流程；<br>5) **渠道分层驱动检索预算**：第一层级优先分配检索配额与深度，预算受限时低层级先降级/跳过；小红书检索优先使用登录态搜索保障全面性（实现机制见设计文档 ADR-4/§5.4，须遵守 NFR-4 授权与合规边界） |
| 验收标准 | ① 对任一目的地，7 类信息类别覆盖率 ≥ 6/7；② 每条展示信息可点击溯源；③ 社媒与平台两类来源均出现；④ **第一层级渠道（小红书/抖音）内容必须出现**（小红书未授权登录态时以 L0+L0.5 抽样内容满足，并标注抽样语义） |

### FR-4 交通方式搜索与组合（P0）

| 项 | 内容 |
|---|---|
| 描述 | 搜索、比较并组合各类交通方式，组织为出行指引 |
| 覆盖范围 | 城际交通：火车票（P0）、机票（P0）、汽车票（P1：v1 以搜索降级+官方购票链接提供，稳定结构化数据源待调研，见设计文档 §4.3/§13）；市内交通：机场/车站 ↔ 市区/住宿点的衔接方式，**提供高德与滴滴双方案的公共交通选项**（用户决策 2026-09-01，见设计文档 §2.1） |
| 详细要求 | 1) 按可靠平台抓取班次、时刻、大致价格档位；<br>2) 至少给出 2 种可行交通方案并从 **时间 / 价格 / 舒适度 / 带娃老人适配** 维度对比；<br>3) 输出"出行指引"：推荐方案 + 备选方案 + 购票提示（渠道、放票时间、候补建议）；<br>4) 价格为参考区间，明确标注"以购票时实时价格为准"；<br>5) 目的地与出发地不通直达时，给出中转组合方案 |
| 验收标准 | ① 每次规划产出 ≥ 2 个可执行交通方案，其中至少 1 个含班次时间与价格档（搜索降级来源的价格可标注为参考区间）；② 市内衔接段（如"机场→酒店"）有明确方式与耗时估计 |

### FR-5 其他出行建议（P1）

| 项 | 内容 |
|---|---|
| 描述 | 搜索并输出其他相关出行建议 |
| 覆盖范围 | ① 天气（行程期间目的地天气预报/气候概况）；② 穿衣建议（基于天气+季节+户外活动强度）；③ 需准备物品（证件、电子设备、药品、装备等清单）；④ 可扩展：当地习俗、安全提示、通讯/支付准备 |
| 详细要求 | 1) 天气需覆盖行程起止区间，超预报窗口时给出气候概况并说明；<br>2) 穿衣与物品清单需结合偏好槽位（如带老人/儿童、徒步偏好）定制；<br>3) 物品清单可勾选/导出（行程页内交互） |
| 验收标准 | ① 天气信息含数据日期与来源；② 物品清单 ≥ 10 项且与用户画像相关 |

### FR-6 行程方案生成（P0）

| 项 | 内容 |
|---|---|
| 描述 | 综合全部检索信息，生成结构化、可执行的行程方案 |
| 输出结构 | ① 总览（目的地/日期/人数/预算假设/一句话主题）；② 按天分组的行程（每日：动线、景点+建议时长、餐饮推荐、住宿区域）；③ 交通方案（引用 FR-4 结果）；④ 避雷与注意事项汇总；⑤ 出行建议（引用 FR-5 结果） |
| 详细要求 | 1) 动线需地理合理（就近成片，避免跨城折返），依据地图工具的距离/路线数据；<br>2) 每日节奏尊重偏好槽位（松/紧、老人儿童适配）；<br>3) 预算槽位存在时给出分项预算估计；<br>4) 支持**增量修订**：用户指出"第二天太满"等反馈后，仅重排受影响部分，不推翻全部结果 |
| 验收标准 | ① 任意两日的动线无地理位置折返冲突；② 修订后未受影响日的 stops（名称/顺序/时长/来源引用）结构逐项相等 |

### FR-7 结果可视化展示（P0）

| 项 | 内容 |
|---|---|
| 描述 | 将搜集到的全部信息组织为可视化 HTML 页面并进行展示 |
| 硬性要求 | 页面中**必须包含实际可用的地图组件**（可交互：缩放、拖拽），非静态截图 |
| 页面内容 | ① 行程总览卡片；② 地图组件：全部点位（景点/住宿/餐饮）标注、按日路线连线、点击弹窗展示详情；③ 按天 Tab/时间轴视图；④ 交通方案对比卡片；⑤ 美食/住宿/避雷信息卡片（带来源链接）；⑥ 天气与物品清单模块 |
| 详细要求 | 1) 行程页为自包含 HTML（或由插件路由在线提供），用户可直接在浏览器打开；<br>2) 地图组件与行程数据联动（点击某日 → 该日点位高亮）；<br>3) 移动端浏览器可正常浏览（响应式）；<br>4) 页面提供行程数据导出入口（至少 JSON/Markdown，P2） |
| 验收标准 | ① 地图可缩放/拖拽/点击弹窗，点位数 = 行程方案中点位数；② 页面在外网浏览器（含手机）可打开且样式不错乱；③ 全部来源链接可点击 |

### FR-8 设置页：渠道开关与 Key 管理（P0）

| 项 | 内容 |
|---|---|
| 描述 | 插件在 DSH 设置页面注册设置页（设置卡），提供**功能渠道开关**与**渠道 Key 管理**两类能力 |
| 功能渠道开关 | 按功能（FR-3~FR-7）分组，**每项功能的每个渠道可独立启用/停用**（如仅停用 FR-4 的滴滴渠道、仅停用 FR-3 的 CloakBrowser 增强渠道）；被停用的渠道在对应功能的检索编排中跳过，并在 `degraded[]` 标注"已停用（用户配置）" |
| 渠道 Key 管理 | 对每个渠道所需的密钥统一管理，支持**新增、编辑、删除、查看**：① 需 key 渠道（高德 Web 服务、高德 JSAPI+jscode、携程问道、flyai、滴滴、腾讯位置服务、CloakBrowser）逐项管理；② 无需 key 渠道明确标注（xiaohongshu-mcp=扫码登录自管会话；dsh-web-search-pro=由该插件自管）；③ Key 值在界面**脱敏显示**（如 `b235****911c`），查看完整值需二次确认 |
| 绑定与持久化 | 开关与 Key 均**按渠道维度绑定**，保存为 DSH 设置的持久化配置项（settings 命名空间，secret 字段脱敏） |
| 生效时机 | 配置保存后**立即生效**（无需重启）：工具每次执行时读取最新配置快照 |
| 联动校验 | 保存时校验每项功能仍保留 ≥2 个启用渠道（NFR-10），不足时给出警示（软校验：允许强制保存，但显示冗余不足警告）；渠道开关开启而 Key 缺失时，该渠道自动视为不可用并在结果中标注，不阻塞其他渠道 |
| 验收标准 | ① 设置卡出现在 DSH 设置-插件页并可正常操作；② 开关切换后，下一次工具调用即按新配置执行（无需重启）；③ Key 的新增/编辑/删除持久化且界面脱敏显示；④ 删除某渠道 Key 后该渠道自动降级并在 degraded[] 标注；⑤ 关闭渠道致某 FR 启用渠道 <2 时出现冗余警示 |

## 6. 非功能需求

| 编号 | 类别 | 需求 |
|---|---|---|
| NFR-1 | 性能 | 单次全流程（槽位确认后 → 行程页产出）目标 ≤ 10 分钟；单个外部工具调用超时（默认 30~60s）+ 重试上限 2 次 |
| NFR-2 | 可靠性/降级 | 任一外部数据源失败时流程不中断：该信息模块标注"获取失败/数据缺失"，其余模块正常产出；整体成功率目标 ≥ 95%（一次成功 = 全流程产出可打开的行程页，且目的地情报/交通/出行建议三模块中降级不超过 1 个） |
| NFR-3 | 数据质量 | 关键信息带来源平台 + URL + 获取时间戳；聚合内容注明"AI 汇总，请以来源为准"；同一对象多来源冲突时并列展示 |
| NFR-4 | 合规 | 抓取行为遵守目标站点 robots 与服务条款，控制请求频率；不抓取付费内容、不做验证码求解；不存储用户第三方平台账号密码类凭据；如启用登录态（会话 cookie/storage_state）抓取，须用户显式授权，会话态文件仅存本机、限期保留、可随时清除（详见设计文档 §5.6） |
| NFR-5 | 隐私与安全 | 外部服务 API Key 通过宿主 credentials/settings 机制存储，不落明文于代码/日志；行程内容仅在用户会话与本地工作区内流转 |
| NFR-6 | 成本 | 外部 API 调用有配额与缓存策略（同类查询命中缓存不重复计费）；单次规划默认调用预算：高德 REST 实调 ≤60 次（其中 POI 搜索 ≤40 次）、外部搜索 ≤30 次，超出即告警并停止新增调用（预算可经插件配置调整） |
| NFR-7 | 可扩展性 | 数据源与工具模块化：新增一个数据源（如新增平台）不改动意图/流程层代码；遵循 DSH 插件标准形态（可热重载、可注入） |
| NFR-8 | 可维护性 | 代码遵循 DSH 官方插件包结构（TypeScript、lib/ 产物、peerDeps 声明）；类型检查零错误 |
| NFR-9 | 可用性 | 全程用户可见进度反馈（正在查什么、还剩什么）；失败时给出人话原因与重试入口 |
| NFR-10 | 冗余性 | **每项功能需求至少保留两个实现渠道，每个渠道均含降级路径**（用户决策 2026-09-01）：任一单一渠道失效时对应需求仍有可用产出（允许降级形态），全流程不中断；验收以设计文档 §2.1 渠道与降级矩阵为准（M3 逐渠道故障注入演练） |

## 7. 数据需求（信息模型概要）

一次旅行规划会话产生并维护的核心数据实体（详细字段在设计文档定义）：

1. **TravelRequest**：planId（规划会话持久化 ID）+ 模式（plan 规划 / recommend 目的地推荐）+ 槽位集合（出发地/目的地/日期/天数/人数/预算/偏好/特殊约束）+ 状态机（collecting → [recommending → collecting] → confirmed → researching → generating → delivered → revising → generating（修订循环）
2. **DestinationIntel**：按 7 类信息组织的目的地情报条目（摘要/来源/时间/置信度）
3. **TransportOption**：交通方案（方式/班次/时间/价格档/渠道/适用性标签）
4. **Itinerary**：按天的行程结构（Day → Stops[]，每 Stop 关联 Intel 条目与坐标）
5. **TravelBrief（成果包）**：以上全部 + 行程页产物路径

## 9. 风险概览（详细缓解见设计文档）

| 风险 | 等级 | 一句话缓解方向 |
|---|---|---|
| 社交平台反爬严格，登录态抓取不稳定 | 高 | 混合策略：官方 API/MCP 优先，搜索缓存与降级兜底 |

| 信息过时误导用户 | 中 | 强制来源+时间戳，过期降权 |
| 外部 API 成本失控 | 中 | 配额、缓存、单次上限 |
